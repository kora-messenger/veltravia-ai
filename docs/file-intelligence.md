# File Intelligence and Artifacts (Step 19)

This is a **development/CI foundation**, not production file hosting. The only concrete byte store is `InMemoryFileAssetStore`: bytes and metadata are process-local and disappear on restart. `FileAssetStore` is the replacement port for durable object storage. No uploaded content is executed, mounted in a runtime, or added to agent system/developer instructions.

## Lifecycle and models

`FileAsset` uses opaque IDs, metadata, source, owner/project/workspace scope, checksum, expiration, optional parent, and a private byte reference. Transitions are validated: `received -> validating -> validated -> ready -> extracting -> ready|derived`, with rejected/corrupted/expired/deleted terminal branches. API views omit byte references. `Artifact` has an independent `creating -> validating -> ready` lifecycle, checksum, expiration and provenance links to parent file/artifact IDs and operation ID. Provenance means _origin_, not correctness or authority.

Sources are `user_upload`, `generated_artifact`, `project_file`, `connected_app_reference`, `imported_archive`, and `derived_extraction`. The public upload endpoint accepts only `user_upload`. Future integrations must use trusted server-side adapters, not client-provided source labels. IDs never derive from filenames.

## Types, extraction and bounds

Magic bytes take precedence over extension and declared MIME. A disagreement is recorded. Binary types require a recognized signature; OOXML containers must contain their expected workbook/document parts. Text fallback requires text-like bytes. The detection list includes TXT, Markdown, JSON, XML, CSV, PDF, DOCX, XLSX, common source code, PNG/JPEG/WebP/GIF, ZIP, WAV/MP3/etc., and MP4/WebM/etc. A recognized container does not imply a complete semantic parser.

TXT/Markdown/code produce bounded text. JSON validates and returns a redacted structured value; XML rejects DTD/entity declarations and gives bounded roots/text; CSV gives headers and bounded rows. PDF gives text and page count where extractable; DOCX gives paragraphs; XLSX gives sheet names, dimensions, headers and bounded cells. Image preview uses only validated image bytes, dimensions and MIME. Audio/video give type, size, checksum and duration where safely detectable; no transcription, OCR, image understanding or video interpretation. `Codebase Intelligence` remains the sole code indexer, and Project Memory does **not** ingest full file contents.

Configured defaults and hard ceilings are in `security/index.ts`: 25 MiB default single file (100 MiB ceiling), 100 MiB default uncompressed archive (500 MiB ceiling), 1000 entries (5000 ceiling), 12 nesting levels (20 ceiling), 100 MiB artifact per operation (500 MiB ceiling), 250,000 extraction characters (2,000,000 ceiling), 8000 preview characters (20,000 ceiling), path length 240 (512 ceiling), and ZIP ratio 100 (200 ceiling). No caller-provided option may exceed ceilings. The JSON/base64 upload route sets a 36 MiB request-body limit and rejects encoded payloads over 34 MiB before decoding. This transport is not suitable for very large production uploads; streaming object-storage ingestion is future work.

ZIP central-directory inspection rejects unsafe paths, case-folded duplicate paths, symlinks, nested archives, entry/size/ratio/depth excess and malformed structures. Preview lists entries **without extracting files**; explicit extraction reads bounded entries into the mock store and registers parent-child lineage. It never unpacks to host directories or runs payloads. DOCX/XLSX use ZIP inspection before reading selected parts.

## Authorization, tools, downloads

File/Artifact manager methods check owner, project and workspace scope; API upload additionally verifies project ownership and workspace membership against Project Engine. The API's development principal is derived from `VELTRAVIA_DEFAULT_OWNER_REF` or the fixed development default, never from an untrusted owner header. Scope-context headers restrict reads when supplied but are **not proof of authenticated identity**. Authentication/session integration does not exist in this monorepo yet, so production cross-user isolation is NOT claimed. Do not deploy this development API as a public multi-tenant file service until an authenticated principal and project ACL are wired server-side.

File tools run through the existing Tool System: metadata and bounded preview are low-risk reads; extraction is permission-gated medium risk; deletion and publication are high risk and require human confirmation. Server-side principal is not tool input. Agent context sees a bounded `untrusted_data` preview, never raw file descriptors, full contents, credentials, permissions, or a second filesystem pathway. API file extraction is an authorized user action, not an agent tool bypass. Project artifact publication passes through Project Engine and then captures an `artifact_publish` revision in the **existing** Version Control, so it can be restored through the existing rollback mechanism. Only text-compatible artifacts may be published to the text-based project tree. Uploaded/global files are not mounted into the preview Runtime automatically.

`GET /api/artifacts/:id/download` issues an opaque short-lived reference and requires owner, scope, ready status and non-expiration. The second request verifies token, size and SHA-256 before streaming bytes with attachment disposition and `private, no-store`. Storage keys/host paths never appear in API views or URLs. Image bytes have a separate, authenticated-scope-checked image route with `nosniff`, sandbox CSP and no-store. UI renders preview text as React text nodes, never HTML; only validated images get an image element. Archive trees display paths as text. Structured audit events carry identifiers, counts and scrubbed values, not file contents. Secret-shaped values in preview/extraction are redacted; raw user-owned artifact bytes are never silently rewritten. A caller must treat downloadable bytes as untrusted data.

## API and UI

File routes: `POST /api/files`, `GET /api/files`, `GET /api/files/:fileId`, `/preview`, `/image` (images), `POST /extract`, `GET /children`, `DELETE /:fileId`. Artifact routes: `GET /api/artifacts`, `GET /:artifactId`, `/preview`, `/download`, `DELETE /:artifactId`, `POST /:artifactId/publish`. Upload JSON includes filename, base64 bytes, optional declared MIME and project/workspace IDs. Scope checks are server-side, not a UI filter. The Files & Artifacts page supports upload, search, lists, badges, details, preview, archive tree, extraction, download and deletion on desktop/mobile. Artifact detail displays source operation and provenance.

### Known limits / future adapters

No production persistence, authenticated identity, streaming multipart ingress, background extraction, virus scanning, remote connected-app retrieval, APK inspection, advanced document parsing, audio/video intelligence, research agent, or billing is included. Large/malformed PDFs and deeply complicated DOCX/XLSX may fail safely rather than fully parse. Media duration is only returned for recognized safe headers and may be null. No file is implicitly exposed to runtime. The next object-storage adapter must implement `FileAssetStore` and preserve scope, integrity and audit checks; no R2 integration is added here.
